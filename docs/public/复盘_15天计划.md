## 二、复盘 loop 1：为什么“大道至简”后效果更好

之前的问题是：

```text
搜索强制规则
  -> query 被拼坏
  -> 搜索污染
  -> 模型没拿到正确信息

答案契约
  -> 强制补“无来源数字”
  -> 模型复制截断片段
  -> 自检再重写
  -> 信息继续丢失

防复读
  -> 相似事实误判
  -> 正确回答被重写
```

结论：

- 不是模型不会答，而是搜索信息没进对。
- 不是补丁不够多，而是补丁互相打架。
- 删除重写层之后，日志中“曼波”从英国歌手变成赛马娘/翻车鱼梗。

## 三、复盘 loop 2：Day11-15 新发现的问题

### 3.1 stats 锁死锁

问题：

`_flush_stats` 在持有 `_stats_lock` 时调用 `get_avg_reply_time()`，后者再次抢锁。

现象：

- 进程启动后卡住。
- `stats.json` 不生成。
- WebSocket 不连接。

修复：

- 在锁内直接计算平均值，不再调用带锁函数。
- 增加测试 `test_flush_stats_writes_file_while_lock_held`。

### 3.2 非管理员指令未忽略

问题：

- 非管理员发送 `!status` 时，`handle_admin_command` 返回 `None`。
- 消息继续进入 LLM，不符合“非管理员静默忽略”。

修复：

- 群聊和私聊入口都判断 `_admin_text(text).startswith("!")`，非管理员直接返回。
- 集成测试覆盖。

### 3.3 搜索统一入口和异步路径没有完全统一

现状：

- `search_with_resilience` 是同步统一入口。
- `search_web_async` 仍保留自己的并发搜索逻辑。
- 两边都接入缓存和引擎降级，但代码入口不同。

这不是 Day11 验收失败，而是后续可以继续收敛的优化点。

## 四、反思：哪些经验值得长期保留

1. **搜索信息质量 > 后处理补丁**
   - 搜索结果对了，回答大概率对。
   - 搜索没有结果时，再多的字段检查都会逼模型编造。

2. **重写层越少越好**
   - 每重写一次就多一次丢信息风险。
   - 能用第一轮结果就直接用第一轮结果。

3. **来源透明比假装准确更重要**
   - `（联网搜过喵）` 让用户能判断答案可信度。

4. **启动检查不能只检查“结果”，还要检查“会不会死锁”**
   - 这次 stats 死锁没有被测试发现，因为测试模式跳过了文件写入。
   - 之后应增加“生产模式启动最小路径”测试。

## 五、剩余优化空间

### 5.1 stats 跨重启持久化

当前 `stats.json` 每次重启后从 0 开始。

优化：

- 启动时读取旧 `stats.json`，只更新 `started_at`。
- 或者区分“本次运行”和“累计运行”两套字段。

### 5.2 搜索入口统一

当前有：

- `search_web` / `search_with_resilience`
- `search_web_async`

优化：

- 把 `search_web_async` 收敛成异步包一层 `search_with_resilience_async`。
- 公共逻辑只保留一份。

### 5.3 DrissionPage 浏览器兜底

现状：

- `QQ_DRISSION_SEARCH=1`，但本机未安装 `DrissionPage`。
- 反爬严重时，浏览器兜底实际不可用。

优化：

- 安装 `DrissionPage`。
- 或增加 `playwright` 方案。

### 5.4 搜索建议和泛百科的过滤仍需观察

已过滤：

- `2026年_百度百科`
- 放假安排
- 日历
- 百度建议进入可靠资料

仍需观察：

- 更多年份百科。
- 词典解释。
- SEO 垃圾页。

### 5.5 长期记忆是否重新启用

当前为了大道至简，主链路不主动注入长期记忆。

优化方向：

- 不重新注入大段记忆。
- 改为“用户明确提到某梗/人物时，只检索对应记忆块”。
- 这样既不会被旧记忆污染，也不会完全浪费已清理的记忆。

### 5.6 集成测试继续扩展

## 六、最终判断

15 天计划的核心任务已经全部完成，可以正常演示和面试讲解。

但“完成”不等于“没有优化空间”。当前最值得做的三件事：

1. stats 跨重启持久化。
2. 搜索同步/异步入口统一。
3. 安装真实浏览器兜底，提升反爬场景下的搜索稳定性。

这三项都不是必须马上做，但做了之后项目会更接近生产级。
