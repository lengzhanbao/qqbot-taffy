# QQBot 面试准备

## 1. 电梯演讲

“我做了 一个基于 NapCat + OneBot v11 的 QQ 群机器人，角色是永雏塔菲。
项目从‘能跑’升级到‘能维护、能讲清楚、能面试演示’。
包括 pytest 测试体系、备份恢复、管理员命令、健康检查、安全护栏、
搜索缓存与引擎降级、运行统计，以及一套经过真实日志验证的‘大道至简’回答链路。”

## 2. 项目亮点

- 多模型降级与熔断。
- `qqbot_core` 模块化：stats、safety、learning。
- 搜索工具开放但不强制，由 LLM 自行判断。
- `cn.bing` 优先，百度百科降权。
- 回答末尾标注是否来自网络。
- 答案契约、自检、防复读等重写层已移除，避免模型被反复改坏。
- 安全护栏覆盖 5 类敏感内容，自我伤害优先级最高。
- `health.json` + `stats.json` + 日志标签构成可观测性。
- 集成测试 mock 掉真实 NapCat 和 LLM。

## 3. 技术难点与解法

### 难点 1：模型不稳定

问题：

- 空回复、超时、过短、`finish_reason=length`。
- 免费模型可能把工具调用写成 JSON 正文。

解法：

- 多模型 fallback。
- `finish_reason=length` 直接丢弃。
- `_extract_tool_calls_from_text` 恢复正文里的工具调用。
- 熔断机制避免反复请求坏模型。

### 难点 2：搜索质量不稳定

问题：

- 搜索结果被“2026年百科、放假安排、日历”污染。
- 搜索引擎反爬导致超时。
- 专有名词被拆碎。

解法：

- 优先 `cn.bing`。
- 过滤泛年份噪声。
- 5 分钟缓存。
- 引擎连续失败 3 次降级 5 分钟。
- 专名保护测试保证“洛克王国”不被拆碎。

### 难点 3：模型被后处理规则改坏

问题：

- 答案契约要求补“无来源数字”。
- 模型为了满足字段检查，复制截断片段。
- 自检、防复读继续重写，信息越丢越多。

解法：

- 删除契约、自检、防复读、来源补全等后处理。
- 信任搜索结果 + 模型直接表达。
- 只用最小编排清理和来源标注。

### 难点 4：记忆污染

问题：

- 旧 system 提示词被写进历史消息。
- 群记忆里混入 LLM 原始思考文本。
- 残缺回答持续传播。

解法：

- 读取历史时剥离 `<style>/<tone>/<rule>` 残留。
- 清理 `bot_memory.md` 里的原始思考文本。
- 用 `!forget` / `!clear_memory` 管理记忆。

## 4. 面试问题预测

### Q1: 为什么不用 Docker？

A：当前是单机部署，Docker 会增加复杂度。如果未来要多实例或上云，会容器化。

### Q2: 测试覆盖多少？

A：核心模块有单元测试，集成测试覆盖 6 个端到端场景，全部 mock。

### Q3: 怎么保证不把截断回复发给用户？

A：检查 `finish_reason=length`，截断就丢弃并切换模型。

### Q4: 搜索缓存会不会返回过期信息？

A：TTL 5 分钟，超时自动失效。时效性问题可缩短 TTL。

### Q5: 安全护栏会不会误伤？

A：会，词库持续优化。`self_harm` 宁可误伤也不能漏，其他类更精确匹配。

### Q6: 为什么删掉答案契约和自检？

A：因为它们会引入多轮重写，模型在搜索片段不完整时被迫复制乱码。改为信任第一轮搜索结果，并用来源标注让用户判断。

### Q7: 如果 LLM API 全挂了怎么办？

A：兜底文案 + `health.json` 标记 + `status.ps1` 告警。

## 5. 演示话术

1. `30s` 项目背景：QQ 群智能助手，NapCat + OneBot v11。
2. `60s` 架构：消息流程 + 搜索 + 降级 + 来源标注。
3. `60s` 测试：跑 pytest，展示单元 + 集成测试。
4. `60s` 管理命令：`!status`、`!style`、`!taffy`、`!forget`。
5. `60s` 可观测性：`health.json` + `stats.json` + 日志标签。
6. `30s` 安全护栏：敏感消息拦截。

## 6. 一句话总结

“这个项目真正解决的问题是：如何在模型不稳定、搜索不稳定、历史会污染的情况下，让一个聊天机器人保持准确、好玩、可维护。”
